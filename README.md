# zinro-game

人狼ログ(zinro.net 形式)から「議論のそれっぽさ」を学び、将来 AI 参加者に組み込むための土台。

## 方針

- モデルの重みは学習しない。厳選したログを読み、知識ファイルに書き出して、あとでプロンプトに載せる。
- 学習結果は `knowledge/` のファイル。ログを足すたびに更新する。
- 口調(方言や口癖)は真似しない。標準語・です/ます調で、会話の型・論理の運び・語彙を学ぶ。
- チャットでは用語や配役を説明せず、説明口調を避ける(AI っぽく見えるため)。
- 会話がしっかり成り立ち、発言量も多い「上澄み」を学ぶ。ベースは話者 B(17本中12本に出る)、次点は話者 A(17本中9本に出る。log11・log12 では別の名前で参加していると、依頼者が教えてくれた)。B・A のいない log13〜log15 は、依頼者が「面白そう」と入れたもので、tier 3 の参考(村人側の摩擦、人狼の動き方、黙る人狼)。log16 は、依頼者が占い入りの6Aとして貼ったもので、A が人狼で出る(B はいない。議論は昼1・昼2の2日)。log17 は、依頼者が通常配役の12A猫として貼ったもので、B・A はいない(人狼3・占い師・霊能者・狩人・猫又・狂人。議論は昼1〜昼3の3日)。12A猫は、チャットの練習部屋より先に、盤面の学習から始める(依頼者の方針。実際の初心者も盤面整理から始める)。可能性を入れながら、今の環境(定番)を確かめ、詰み進行などを学ぶ。log17 の知識は `knowledge/normal_12a.md`、盤面の知識は `knowledge/board_12a.md`(依頼者に聞いた環境での扱いも入っている)。依頼者が持ち込んだ 11A の確率論のまとめは `knowledge/prob_11a.md`(12A猫ではなく、前提が今の環境とずれているので、第1部の考え方だけ使う)。log17 の H(log13・log14 の D、log15 の C と同じ人)と C(log08 の C と同じ人)は、依頼者が「しっかり発言出来ている」と評価している。C 以降は相手側の動きの参考にとどめる。発言例の `tier` は 1 = B、2 = A、3 = その他。`register` は敬語／タメ口(どちらでもよい)。
- 目標の水準は、B・A 級の「超人型」。B・A が同席した4A(最初の4本)の発言の質と量を基準にし、相手が誰でも落とさない。相手が短く返す部屋でも、量を合わせて下げない。依頼者の見立てでは、最初に見せた 1448556 が最も手加減していない(これを力を出す局面の基準にする)。log07・log08・log12 のような雑談の長い軽い試合も、冗談を挟む呼吸の手本にする。
- B・A は入力速度が「人外」と呼ばれるほど速いとされる(依頼者の伝聞)。こちらの想定の数倍は速い前提で設計する。字/分の実測は、読む・考える時間を含んだ平均で、入力速度の上限ではない。
- 1つの発言に1つ返すだけではない。連投で畳みかける、複数の発言をまとめて受ける、前の発言に遅れて返す、返さない発言がある。この構造も学ぶ(`knowledge/reply_structure.md`)。発言例には、受けている発言(`reply_to`)を付ける。
- 特定の人を悪く言う雑談が混じるログは、依頼者が許容したもの(例: 次戦に参加する予定の常連についての、根も葉もない冗談で、本人も気にしていない)でも、中身は知識ファイルに書かない。雑談の形(長さ、役割、切り替え)だけを使う。ボットは、本人が気にしないかを確かめられないので、人を話題にして悪く言うことを自分から始めない。
- 長文は、一文ごとに意味があるときだけ。冗長な言い直しや、観点の羅列は避ける(AI は冗長になりやすいため)。量は投稿数と論点の数で稼ぐ。

## 使い方

```
python -m zinro_learn ingest logs/raw/<id>.txt --players "実名1=A,実名2=B,実名3=C" --alias 通称=実名1 --discussion-seconds 300
python -m zinro_learn stats logs/normalized/<id>.json
python -m zinro_learn timeline logs/normalized/<id>.json   # 役職、夜の行動と通知、死亡、人狼の夜チャットを、夜と昼の順に並べる
python -m zinro_learn board knowledge/boards/<id>.json     # 盤面整理: 段階ごとの、合う役職の割り当て(真・狼・狂)、定番／ありうる／まれ、名乗った人の種類の見込み、確定した黒白、縄
python -m zinro_learn board --patterns                      # 名乗りの数(占い-霊)ごとの、名乗りの種類の組み合わせ
python -m zinro_learn progress --seers 3 [--result A:B:黒] [--cat off|hidden|open|counter]  # 進行の比較: 12A猫の3-1などで、グレー・占いロラ・黒スト・ロラ完遂の、村の勝率の試算(村の読みなし。占いの2日目以降の夜の結果、猫又の道連れ、人外側の同数の票(RPP)あり。--no-seer-results、--no-rpp でなし。counter は猫が名乗り、対抗猫が出て猫吊り)
python -m zinro_learn sync      # 発言例から、ガイドの「発言の型」の表を作り直す
python -m zinro_learn check     # knowledge/ の整合性を調べる(問題があれば終了コード 1)
python -m zinro_learn structure # 連投と返信の型を数える(発言例の reply_to を使う)
python -m unittest
```

- ログは新しい発言が上のままで貼ってよい(並びは自動で判定する)。ゲーム開始から勝利の通知まで、「鯖→」の個別通知も含める。
- `--discussion-seconds` は1日あたりの議論時間(延長前の秒数)。指定すると字/分を出せる。延長は、ログの通知から数える(300秒 + 90秒 × 回数。3回なら570秒、2回なら480秒)。
- 本文中の通称(例: ハンドル名の略称)は `--alias 通称=実名` で匿名化の対象に加える。ハンドル名がふつうの語句でもある人(例: 「なるほどね」のような名前)は、`--plain-word 名前` も付ける。`logs/private/<id>.players.json` の `plain_words` に入り、`check` の実名混入の検査から、その表の分だけ外れる(同じ名前が別の表で実名として載っていれば、そちらでは調べる)。
- 議論が2日以上のログ(占い入りの6A、通常配役の12A猫など)は、`stats` が日ごとの発言数・字数・延長・字/分も出す。議論時間は、日数 × `--discussion-seconds` + 延長の合計で割る。議論時間が分からないログは、`--discussion-seconds` を付けない(字/分は出ないが、日ごとの件数と字数は出る)。
- 人狼の夜チャット(「X→人狼: …」)は、`wolfchat` として分け、発言に数えない。人狼の役職通知の「仲間は【…】です」も読む(取り込み後の players の mates)。
- 霊界(死者・観戦者のチャット)と自分宛ての行は、発言として数えない。プレイヤー以外の名前は O1, O2… に匿名化する。
- 勝利の通知より後の発言は、ゲーム後の雑談として `after` に分け、発言として数えない。名前に「：」を含む人(例: 「RE：〇〇」)も、役職通知から名前を拾って読む(`--players` にもそのまま書ける)。
- ログを足す手順: `ingest` → `stats` → 発言例を `knowledge/examples.jsonl` の末尾に追記(話者ごとの `tier` と `register`、その発言が受けている発言の seq `reply_to` を付ける) → `sync` → 表の「(要記入)」を埋める → `check` → ガイドと立ち回りメモを更新。`check` は、発言例とログの突き合わせ(`reply_to` を含む)、表のずれ、実名の混入、説明口調の語、原文との18字以上の一致を調べる。

## ボット(試作)

貼ったログを読んで、次に書く発言の案(0〜4件)を返す。zinro.net には接続せず、投稿は人間が行う(自動投稿はしない)。知識は `knowledge/` から組み立てる(重みは学習しない)。

使い方は3通り。

1. API(キーが要る): 環境変数 `ANTHROPIC_API_KEY`(または、リポジトリ直下の `.env`)を設定して、ログを渡す。
   ```
   python -m zinro_bot reply ログ.txt --me 名前 --role 人狼 --remaining 200
   pbpaste | python -m zinro_bot reply - --me 名前
   python -m zinro_bot reply ログ.txt --show-transcript   # 読み取った発言者・並び・番号の確認
   ```
   役職通知が1人分だけのログなら、`--me` と `--role` は省ける。`--model` で変える(既定は `claude-opus-5-5`、環境変数 `ZINRO_BOT_MODEL` でも指定できる)。`--effort low` で考える量を減らす(速く、安くなる。Opus 5.5 は思考を切れないので、量で調整する)。`--register 敬語` で語調を変える。
   `--session 名前` を付けると、前のターンの読み(各人の立場、未回収の問い、票先の見込み)を `logs/sessions/`(git 管理外)に残して、次のターンに渡す。ゲームの途中で言うことが変わりにくい。`--critic` を付けると、出した案をもう一度点検させる(呼び出しが1回増える)。
2. Claude Code(キーは要らない): このリポジトリで、`zinro-player` スキルに、ログを貼って頼む。
3. Claude のプロジェクト(キーは要らない): `python -m zinro_bot prompt --me 名前 --role 村人 --format chat --out prompt.txt` の出力を、プロジェクトの指示に貼り、ログを貼って頼む。

手元で試す(zinro.net には接続しない): `python -m zinro_bot chat --me ボット --role 村人 --players あなた,相手`。「名前: 発言」で相手役を自分で打ち、空行でボットの番。`/残り 200` で残り時間、`/延長`、`/投票`(投票時間にする)も使える。毎ターンの所要秒を出し、`/quit` で、ターン数・所要時間の平均と最大・1ターンの量を集計する。モデルを呼ばずに流れだけ見るなら `--fake`。

作りの要点(「超人型」への対応):

- 量と構造: 1ターンに 0〜4件を、返信先(`reply_to`)つきで出す。連投、複数への返信、数件前への返信を許す。ログから機械的に拾った「未回収の問い」と「文字量の割合」を添える。
- 読み: 出力の `read` に、発言者ごとの立場・基準・矛盾を先に書かせてから、発言を書かせる。
- 検査: 説明口調の語、方言、箇条書き、例文の写し(18字以上の一致)、長すぎる発言、役職の漏れを検査し、落ちた投稿は理由つきで出し直させる。落ちたままの投稿は捨てる。
- 発言例: 型ごとに B・A(tier 1・2)から選び、役職に合うものを優先する。裏目に出た動き(`outcome=avoid`)は「避ける動き」として見せる。
- 守っていること: 本気で人間かAIかを聞かれたら嘘をつかない。ゲームに参加していない人を悪く言わない。

評価: 過去のゲームを途中まで再生して、ボットの出力と実際の発言を並べる(そのゲームの発言例はプロンプトから除く)。

```
python -m zinro_bot eval --game log08:A --game log10:B --k 3   # 要 API キー。--fake なら流れだけ確認
```

ケースごとに、直前の流れ・実際の発言・ボットの案・票(実際の票と、狼)・所要秒を並べ、最後に、所要時間の平均と最大、1ターンの量、検査で捨てた投稿、村人役の票が狼に当たった数を集計する。使うのは `logs/normalized/`(git 管理外。他のプレイヤーの発言を含むため)なので、別の環境で動かすときは、先に `ingest` でログを作り直す。別のモデルや人の出力で評価するときは、`cases` でケースだけ作り、出力を `eval/out/<ケース名>.json` に置いて `score` する。

速度について、測れるのは、モデルの応答時間(所要秒)と、1ターンの量。打つ速さと返信の間は、ログに時刻がないので、B・A と比べる基準がない。コピペ運用では、貼る人の手が律速になる。

### 練習部屋(ブラウザ。キー不要)

1人+AI の議論ルーム。議論の長さを25〜660秒(5秒きざみ。本戦の300秒と、延長1〜4回の390・480・570・660秒は、ボタンでそのまま選べる)で選び、そのあいだ、ぶっ続けで話して、投票する。AI は、25秒ぶんを先に書くのではなく、あなたや相手の発言を見て、そのつど返す。zinro.net には接続しない。

配役は3通りで、設定で選ぶ。

| 配役 | 構成 | 進み方 | AI |
|---|---|---|---|
| 占いなしの4A | 人狼1・村人2+初日犠牲者(ダミー) | 昼1の投票で決着 | ブン・シン |
| 占い入りの4A | 占い師1・人狼1・村人1+初日犠牲者 | 昼1の投票で決着 | ブン・シン |
| 占い入りの6A | 占い師1・人狼1・村人4(初日犠牲者を含む)。生き残りは5人 | 昼1 → 夜(占い・襲撃) → 昼2。縄は2本で、2本とも外れると人狼の勝ち | ブン・シン・レン・ミオ |

「ブン」は、B・A の動きを写したボット(`knowledge/` から組み立てたプロンプト)。ほかの AI は、ふつうの参加者(短い指示だけ)。

```
python -m zinro_bot room --out room.html   # ページを作る(プロンプトを埋め込む)
```

作った `room.html` を、Claude の Artifact として公開して開く。モデルの呼び出しは、Artifact の `sample` 機能(閲覧者自身の Claude 利用枠)なので、API キーは要らない。初回は、Claude を使う許可の確認が出る。

- 進み方: 開始と同時に、ブンとシンが最初の発言(おはよう。たまに軽い一言を足す)を、モデルを待たずに出す。そのあとは、新しい発言を見るたびに、AI がモデルを呼び、8秒ぶんほどの発言(出す時刻と返信先つき)を、1行1 JSON で書かせる。届いた行から順に、打つ時間(設定の速度。長い発言は貼る扱いで、遅れは最大3秒)を空けて出す。新しい発言があると、まだ打っていない予定は捨てて、見たうえで書き直す。あなたの発言と名前の呼びかけには、特に早く返す。誰も話さないときは、自分から話す。議論の終わりぎわ(残りが、長さの3割か20秒の短いほう以内)は、終わりまでの発言をまとめて頼み(呼び出しは最大3回の頼み足し)、最後まで黙らない。残りが6秒以内(短い議論では長さの15%まで)のあいだは、作り直しが間に合わないので、予定の発言を捨てずにそのまま出し、間に合わない発言は、打つ時間を縮めて、終わる0.3秒前までに出す。判定役は、終わりぎわも黙ったまま。
- 話し方: 新しい発言ごとに返す(挨拶・相づち・笑いだけの発言は除く)。相手の発言と、自分の発言の意味に返す。狼目・村目の評価は、考えて本当にそう思ったときだけ、理由を添えて言う。理由がなければ、聞くか、相手の発言に返す。誰が狼か、吊り先は、終盤まで出さない。短文と長文の両方を使い、長文は B の水準(意味が通り、水増しがない)を保てるときだけ。雑談から議論への切り替えは求めない。同じ問いは2回まで、答えが返った問いは聞き直さない。票先に触れるのは、言って誰がどう動くかを考えて、価値がある場面だけ(毎回はしない。議論全体で2回まで)。自分以外の全員を同じ強さで見て、1人だけを攻めず、もう一人と同じ相手を同じ理由で重ねて攻めない(ページが、名前を出した・返信先にした回数と、票先に触れた回数を数えて、偏りと上限を知らせる)。発言に内部の番号(#12 など)を入れない(混入は、結果の画面に件数が出る)。
- 場の形(占いなしの4A): 「ふつう」は、ブンとシンの2人と話す。「判定役」は、あなたとブンが対話し、シンは、どちらにも肩入れしない判定役になる(3人戦の第三者)。シンは、賛成・反対、狼目・村目、票先を議論のあいだ出さず、口数は少ない。意味がはっきりしない発言の意味を聞く、議論が止まって60秒以上たったら二人に同じ問いを1回だけ向ける、名前を呼ばれたら短く中立に答える、くらいにとどめる。答えの催促はしない。決め手は、ふつうの人狼プレイヤーが使う材料を総合したもの(食い違い、疑いの根拠、疑われたときの反応、動機、読みの更新、具体性)で、「答えなかった」ことだけでは狼と見ず、口の巧さ・発言量・自信の強さ・押しの強さでも決めない。ブンは、判定役への呼びかけを、議論全体で2回までにする。人狼は、あなたかブンで、シンは村人。最後の投票は、シンの1票が決め手になる。判定役のシンの呼び出しは、呼ばれたとき・発言がたまったとき・長く静かなときだけ。
- 占い入り(4A・6A): あなたの役職とブンの役職は選べる(ランダムも可)。残りは無作為に配る。占い結果は、zinro.net の通知の言い方(「◯◯さんは人狼ではありません」「◯◯さんは人狼です」)で、占い師本人にだけ出る。夜は、占い師が1人を占い、人狼が1人を襲う。あなたが占い師・人狼のときは、夜の画面で選び、AI の夜の行動は、それぞれモデルを1回呼んで選ばせる(失敗したときは、候補からの代わりの選び方で進む)。初日の占いは、「お告げ(ランダムな白。既定)・ランダム・占い師が選ぶ」から選べる。zinro.net でどれになっているかは確認できていない(log16 の6Aの占い師は、初日に白を得ている。log17 の12A猫の占い師は、初日に黒を得ていて、「初日は必ず白」ではない。選んだのか自動のランダムかは、ログから決められない)。同票のときは、無作為に1人を処刑する(サイトの扱いは未確認)。死んだあなたは観戦になり(入力欄が止まる)、死んだ AI は話さない。ログのコピーは、日ごとの投票表・夜・朝の通知を含めて、zinro.net の並び(勝利の通知が先頭、役職の通知が末尾)で出る。
- 6A の指示: log16 の言い方(昼の最初の挨拶の中で「おはよう（占いco)◯◯白」と名乗る、吊り指定の出し方と、一致したらそのまま吊る運用、相互票)と、確率論メモ(`knowledge/seer_6a7a.md`)の結論(6A は占いを即露出する、人狼は初日に占いを騙れない、人狼は露出した占い師を襲う、白を出した相手は確白で昼2を決める、最終日の対抗COは五分、縄は2本)を元にする。初日の占いが黒だったとき(設定が「ランダム」「占い師が選ぶ」)の動きも入れた(黒先が人狼なので、黒先を吊る。2人が名乗ればロラ)。占い入りのログは log16 の1本だけで、B はいない(A が人狼)ので、占い入りのブンの動きは、B・A を写したものではなく、この1本とメモからの設計。占い入りの4A(生き残りは3人。占い結果が1つあれば人狼が確定する)の指示は、ログにもメモにも元がなく、ルールから導いたもの。
- 発言例の範囲: 通常配役(12A猫)のログ(log17)の発言例は、4A・6A のブンの指示には入れない(霊能・狩人・猫又・人狼3人まわりの話が混じるため。`zinro_bot/prompt.py` の `GAME_FIELD`)。12A猫の練習部屋を作るときに使う。
- 同時に呼ぶ数: Artifact の `sample` は、同時に動くのが2件ほどで、数件は待たされ、あふれると `rate_limited` で断られる。そこで、ページ側で同時に呼ぶのを2件までにして、あとは順番待ちにする(ブンの発言と、夜・投票の呼び出しを先に。順番待ちの間に不要になった呼び出しは、中断して何も使わない)。AI が4人の6A では、応答の遅い階級だと、順番待ちで発言が遅れる。
- 設定: 配役(占いなしの4A・占い入りの4A・占い入りの6A)、占い入りのときは、あなたとブンの役職と初日の占い、応答(速い=quick・標準・高精度。階級が上がるほど、考えてから書くので遅い)、AI の打鍵速度(5・9・16字/秒、既定は16。ページが表示を遅らせる設定で、モデルの速さではない。ログに時刻がなく、B・A の実際の打鍵速度は不明)、誰が人狼か(占いなしの4Aだけ)、語調。
- 呼び出しの回数: AI は発言のたびに呼ぶので、長い議論ほど増える(模擬の速い応答で660秒を回したところ、2人ぶんで400回ほど。実際の応答はもっと遅いので、これより少なくなるはず)。6A は AI が4人で、昼が2日あり、300秒 × 2日を模擬の速い応答で通したところ、約500回(発言492回[ブン62回、シン・レン・ミオが各140回ほど]、投票7回、夜の行動2回、接続の確認1回)で、同時に動いたのは最大2件だった。入力の量は、ブンの1回が約3万5千字、ほかの AI は、議論の記録が長くなるぶん1回が約1万5千字で、この約500回の合計は約910万字(模擬の実測。入力は、呼び出しごとに送る文字数の合計)。1ゲームでこの量を、閲覧者自身の利用枠から使う。応答は「速い」を勧める。気になるときは、議論を短く(60〜120秒)する。結果の「呼出」で数が分かる。
- 結果: 投票、処刑、勝敗(占い入りでは、日ごとの投票表と、襲われた人、占い師の結果も)。計測は、呼び出しごとの最初の文字まで・全体の秒、あなたの発言から AI の最初の発言までの反応時間(あなたの発言を見たあとに書かれた発言だけを数える)、件数・字数・割合・字/分、説明口調の語の数、最長の発言。診断(呼び出しの記録)と、ログ(zinro.net の形式)はコピーできる。
- Claude を呼べない環境(アプリの外で開いた、許可しなかった)では、定型応答のデモで動く。AI は動かない。
- 確かめたこと: 模擬の `sample` をつけたブラウザ(Playwright)で、設定 → 議論 → 投票 → 結果、挨拶が最初に出ること(遅い応答の階級でも。あなたが開始直後に発言しても)、あなたの発言に返事が付くこと(古い予定を捨てて書き直す)、連投されても返事が出ること、黙っていても話し続けること、500字の長文が切れずに出ること、中断と作り直し、遅い呼び出し、エラー(許可なし・混雑・利用不可)、実時間での25秒、660秒(延長4回ぶん)の通し、最初の発言まで3秒かかる応答での終わりぎわ(75秒の議論で、AI の最後の発言が、終わりの6.8秒前から1.2秒前になった)、各人への発言の偏りと票先に触れた回数が、プロンプトの機械メモに正しく入ること(判定役の形では、ブンに偏りの欄を出さず、判定役にはどちらも出さない)、スマホ幅と暗い配色、コピー。占い入りは、同じ模擬の `sample` で、4A(59項目)と6A(47項目)を確かめた。設定画面(配役ごとの表示、保存と復元)、役職の割り当て(あなたとブンの指定、残りの無作為)、あなたが占い師のときの夜の画面(人狼を占う・村人を占う、お告げ、結果を変えられないこと)、AI の夜の呼び出し(占いと襲撃、候補)、AI に占い結果が漏れないこと、占い師の名乗りの拾い方、昼2(死んだ人は話さず、呼ばれない。あなたが死ぬと観戦)、あなたが人狼のときの夜の襲撃、勝敗(5・4・3人生存、狼が1人のとき)、ログのコピーの順序と夜の行、同時に呼ぶのが2件までであること。Claude を呼べないとき(許可しない)の定型応答のデモも、6A(あなたが村人・占い師)と占い入りの4A(人狼)で、モデルを呼ばずに最後まで通る。代役のモデル(Haiku は「速い」、Sonnet は「標準」の代わり)では、指示を直す前に5回、出力が1行1 JSON の形式どおりに返り、ページの読み取りで全部読めた。指示を直したあとの代役での確認は、別に行う。占い入りの6Aは、模擬のページを実際に進めた状態から入力を取り出して(ブンが占い師・人狼のとき、ふつうの AI が村人・人狼・占い師のとき、夜の占いと襲撃、投票)、代役の8件(Sonnet 7、Haiku 1)で試した。8件とも、1行1 JSON の形式どおりに返った。占い師は、挨拶のあと、結果つきで名乗った(「占いCO。ミオ白」と、吊り指定の持ちかけ)。人狼は、占い師に対抗せず、村人として話した(強い人狼は、対抗が出ていないので占い師を本物で見ていると言い、ほかの二人に聞いた)。夜は、占い師がグレーの1人を占い、人狼が名乗り済みの占い師を襲い、占い師の投票もグレーの1人だった。一方、機械メモが、他人の「占いCO確認」を名乗りに数えて「2人が名乗っている(対抗)」と出し、代役の3件がそれを誤検出と気づいて無視した。返事や伝聞(「占いCO確認」「ブンの占い結果が本当なら」「占い結果を待つ」)は名乗りに数えない形に直した(直したあとの代役での確認はしていない。ページのテストと、言い回し31通りの判定で確かめた)。8件の目視で、強さの測定ではない。
- 確かめていないこと: 実際の `sample` の応答の速さと、出力の書式の守り方(開発環境から呼べない)。診断のコピーで、実際の様子を確かめられる。6A を実際の `sample` で通した結果(呼び出し数、順番待ちの長さ、昼2の様子)。zinro.net が、初日の占い(お告げか選択か)、同票、ダミーを占えるか、昼2の議論時間をどうしているか(ページは、お告げの白、同票は無作為、ダミーは占えない、昼1と昼2は同じ長さとしている。log16 は、昼1が570秒、昼2が390秒)。

### zinro.net に参加者として入れる(全自動)場合

上の3通りは、どれも人が貼る(半自動)。ボットが自分でチャットを読み、自分で打つ全自動には、次が要る。どれも作っていない。

- 人手なしでモデルを呼ぶこと。実質、API キー(従量課金。claude.ai の契約とは別)。Claude Code のスキルとプロジェクトは、人が毎回操作するチャットなので、無人にはできない。
- zinro.net のチャットを読み、書く部分(接続、発言の取り込み、投稿、投票の操作)。方針として作らない。サイトの規約でボットや AI の参加が許されるかも未確認で、使う人が運営に確かめる。開発環境から zinro.net には届かないので、作っても試せない。
- 発言の間の制御(いつモデルを呼ぶか、連投の間隔、1分あたりの上限、止める操作)。

すでにあるのは、ログの読み取り(`transcript.py`)、プロンプト、検査、返信先つきの投稿案(`engine.respond`)。足りないのは、入出力とタイミングだけ。

評価の結果(キーがないため、別の Claude(Opus)をボットの代役にして、log07・08・10・11・12 から序盤と終盤の10ケース。2回目): 序盤の出しすぎ(1件・5〜30字が目安)、早すぎる議論への切り替え、キャラ(怒った冗談など)の崩れは、プロンプトと機械メモの調整で収まった。終盤は、基準を問いの形で聞く、相手の基準を相手に返す、票先を一つに寄せる、といった B・A の動きが出る。一方、log07 の終盤では、前に自分が疑っていた村人(実際は村人)を引き続き疑う案が出た。前の発言を引き継ぐ規則と、もう一人の村人を理由なく狙わない規則の板挟みで、読み(誰が狼か)は材料が少ないと外れる(3人卓の読みは五分五分に近い)。10ケースの目視なので、強さの測定ではない。

未確認: 実際の API 呼び出し(開発環境にキーがなかったため、台本クライアントとテストだけで確認)、実戦での強さ(B・A との比較)、返信の間(時刻のあるログがない)。サイトの利用規約でボットや AI の補助が許されるかは、使う人が確かめる。

## 次にほしいログ

採用の基準: ベース話者 B・次点話者 A が出ているログを優先する。出ていないログは、下の穴を埋めるものだけにする(発言例は tier 3 にして、手本には使わない)。

17本の時点で、足りないもの:

- B・A が人狼で勝ったログ(B・A が人狼の6本のうち、勝ちは log10 の B の1本だけ)
- B・A が全力で話している試合(依頼者の見立てでは 1448556 が最も手加減していない。log07・log08・log12 は軽い試合)
- B・A が出ていて、相手の発言が多く、読み違いの少ないもの(log05・log06 は、相手が短かった。log11・log12 の第三者は、発言が全体の41%以下)
- 占い入りは log16(6A)と log17(12A猫)の2本。log17 で埋まった穴: 対抗CO(偽の占いが霊能の結果で決着)、黒の結果、霊能・狩人と護衛、人狼3人の通常配役。足りないのは、7A、B・A が出る通常配役、占い師が昼2まで生きる場、猫又の能力が出る場、初日の占いの規則(選ぶのかランダムか。6A でも黒が出るのか)が分かるもの、議論時間が分かるもの。log11 の試合後の雑談に通常配役の進行の質疑があるが、実戦の議論ではない
- 発言の時刻が入っているもの(今は返答の速さと入力速度が測れない)
- 村人の勝ちと人狼の勝ちの両方(今は村人側の勝ち11、人狼側の勝ち6。人狼側の勝ちのうち、B・A のいる試合は3本)
